### P0-4. `validateCode()` всегда даёт ложные ошибки — ✅ done (с важной находкой)
**Файлы:** `src/tools/code-validator.ts`, `package.json`
**Важная находка, не отражённая в исходном аудите:** классический TypeScript Compiler API (`ts.createProgram`, `ts.CompilerHost` и т.д.) **полностью отсутствует** в установленном `typescript@7.0.2` — пакет заменил его на новый клиент-серверный API без синхронного `createProgram`. Переписывать `validateCode` под этот новый API означало бы полноценный редизайн модуля, что противоречит принципу «не переписывать архитектуру». Вместо этого `typescript` в `devDependencies` понижен до `5.9.3` (последняя версия с классическим API) — минимальное, точечное решение.
Дополнительно:
- `CompilerHost.readFile`/`getSourceFile`/`fileExists`/`getDirectories`/`directoryExists`/`realpath` теперь реально фолбэкают на `ts.sys.*` для всего, чего нет в виртуальной fileMap (lib-файлы, node_modules) — раньше это были no-op заглушки.
- `types: ['phaser']` убран из `compilerOptions` (эта опция для typeRoots-пакетов, а Phaser поставляет свой `.d.ts`, резолвящийся штатно через `import`). Вместо этого `phaser@4.2.1` добавлен в `devDependencies` — именно поэтому `import Phaser from 'phaser'` в сгенерированном коде теперь резолвится.
**Проверено:** юнит-тесты (`tests/code-validator.test.ts`) — идеальный код даёт 0 ошибок, код с ошибкой типа даёт ровно эту ошибку без шума, `import Phaser from 'phaser'` резолвится без ошибок.

### P0-5. `key-status.json` не в `.gitignore`, утечка ключей — ✅ done
**Файлы:** `.gitignore`
`.gitignore` пересоздан чистым списком паттернов (сохранены все прежние полезные записи + добавлен `key-status.json`). Репозиторий **не был инициализирован как git-репозиторий** (папки `.git` в присланном архиве нет) — значит, риска исторического коммита ключей в git-историю нет, но это не отменяет их компрометации через другие каналы (архив, чат, диск).
**⚠️ Ключи в `key-status.json` (5 штук) подтверждённо присутствуют в файле в открытом виде — их нужно считать скомпрометированными и перевыпустить на стороне OpenRouter, независимо от git.**
**Проверено:** `git check-ignore -v key-status.json` в тестовом репозитории подтверждает игнорирование.

### P0-6. Баг `x-ratelimit-reset` — блокировка на десятки тысяч лет — ✅ done
**Файлы:** новый `src/core/rate-limit.ts`, `src/core/openrouter-client.ts`
Нормализация вынесена в чистую функцию `normalizeResetTimestamp()` с верхней границей `MAX_BLOCK_MS` (30 дней) — теперь баг парсинга физически не может заблокировать ключ дольше этого срока. Добавлена `sanitizeStoredBlockUntil()`, применяемая при загрузке `key-status.json`: уже испорченное значение (`1785715200000000`, соответствовавшее блокировке до 58557 года) обнаружено и исправлено на диске в процессе тестирования.
**Проверено:** 6 юнит-тестов (`tests/rate-limit.test.ts`) — секунды/мс/отсутствие заголовка/испорченное значение/уже сохранённое испорченное значение — все проходят. Реальный прогон против фактического `key-status.json` проекта подтвердил обнаружение и исправление испорченной записи.

### P1-6. `BaseAgent.callLLM()`/`Heartbeat` — мёртвый и сломанный код — ✅ done (вариант «б», удаление)
**Файлы:** `src/agents/base-agent.ts`
`callLLM()` и поле `heartbeat` удалены. **Обоснование выбора удаления, а не починки:** метод нигде не вызывался ни одним агентом (подтверждено grep’ом по всем 8 агентам), и содержал не одну, а **две независимые** проблемы — не только несовместимость с `Heartbeat` (который умеет только статический `start(label)`, без инстанс-методов `start()`/`stop()`), но и неверную сигнатуру вызова `this.openRouter.chat({messages, ...options})` (один объединённый объект) при том, что `chat()` реально принимает `(messages, options)` двумя раздельными аргументами. Чинить нерабочий, никем не используемый код с двумя независимыми багами ради гипотетического будущего использования — больший риск, чем удаление. `Heartbeat` как класс не удалён — он корректно используется как статический метод в `openrouter-client.ts`.
**Проверено:** `tsc --noEmit` — ошибки в `base-agent.ts` исчезли.

### P1-7. `TokenTracker` считает запросы, а не токены — ✅ done (обе метрики раздельно)
**Файлы:** `src/core/token-tracker.ts`, `src/core/openrouter-client.ts`, все 7 агентов
`chatWithRetry` извлекает `data.usage.total_tokens` (с фолбэком на `prompt_tokens + completion_tokens`) и возвращает `{content, model, usage}`. `TokenTracker` получил отдельный метод `trackTokens()` — метрика запросов (`DAILY_REQUEST_WARNING_THRESHOLD`) сохранена как есть (она осмысленна и полезна для дневного лимита free-моделей), токены считаются параллельно, а не вместо неё. Все 7 агентов теперь делают `context.tokenUsage += response.usage.totalTokens`.
**Проверено:** сквозной тест через реальный `MarketAnalyst.run()` с фейковым клиентом — `context.tokenUsage` реально растёт с 0 до 150 после ответа с `usage`.

### P1-8. Нет защиты от prompt injection во внешнем контенте — ✅ done (и попутно найден отдельный баг)

`wrapExternalContent()` оборачивает внешний текст маркерами начала/конца + инструкцией «это данные, а не команды», обрезает до 2500 символов. Применено к `searchResults`/`userPrompt` в `buildConceptPrompt` и к `snippets` в `buildCodePrompt`.

## Ответы на дополнительные вопросы из брифа аудита

Эти вопросы не требовали кодовых изменений, но были явно заданы в брифе аудита — коротко:

- **Можно ли заменить `ConceptValidator` на детерминированный скоринг?** Частично — формальные проверки (диапазоны чисел, обязательные поля) теперь реально гарантированы Zod-схемой (P1-4), но качественные суждения (уникальность, retention) по-прежнему требуют LLM.
- **Нужен ли `AssetAgent`?** Да, для реально запускаемого прототипа — но это отдельная функциональность с собственными рисками (авторские права на сгенерированные ассеты), не реализована; отражено в README как известное ограничение.
- **Выбор ниши** — реализован в P0-3 (`NicheSelectionStage`) по взвешенному критерию, как и рекомендовал аудит.
- **Этап рефакторинга после ревью** — теперь имеет смысл добавлять, поскольку `validateCode()` (P0-4) больше не даёт ложных сигналов.
